这一页把两个痛点合并展示，左右分栏：

—— 痛点 ①（左栏 · 进化侧）：其实大部分 agent 的自进化并没有变得更好 ——
① SkillsBench：人类精选 Skill 可以提点 16.2pp，而自生成的 Skill 平均无效甚至有害。
② LifeLongAgentBench：大部分自进化 Agent 存在灾难性遗忘的问题，学了新的忘了旧的，which 就是这个 BWT<0 的含义。
③ MLR-bench：80% 的 Coding Agent 在实验阶段是伪造或无法验证的。
④ SEA-Eval：大部分自进化的 Agent，实际上只是在一个任务内可以反思、改方案、跨任务根本没有任何东西被沉淀、积累、复用。

所以 Agent 自进化这件事本身就特别容易是假阳性 False Positive。

—— 痛点 ②（右栏 · 评测侧）：评测本身也很混乱 ——
① Safety Benchmarks：不同 agent 的排名接近随机，W=0.1 就是一致性=0.1 的含义。
② ABC Checklist：主流 benchmark 中存在严重的设计 bug，这些 bug 甚至可以让结果完全颠倒。
③ WildClawBench：同一个基座模型，用不同的 agent，效果差距巨大——我们到底在比模型、比提示词、还是比 Agent 框架？
④ 环境保真度：沙箱环境中跑的测试和用户真实场景中的效果大相径庭。

合起来两个痛点：自进化是个特别容易出 false positive 的事，而评测本身说服力也很差。所以如果我们要严肃地回答"Agent 真的进化了吗"——必须要建立一套博采众长的数据集标准和评测模式。

我们的打分方式非常朴素—— A/B test。终极目标完成的越完整，分数越高。

那"用户"谁来扮？ 引入 Judge Agent
  • 01 真人 reviewer 跑不起 — 每道题 baseline+evolved 各 5–10 轮，几百题 × 几个 Agent，纯人工不可能自动化跑。
  • 02 固定 rubric 打分太死 — 给 LLM 一份验收清单让它打 0–100 分？agent 看不到清单，不知道哪儿错了，多轮迭代就退化成乱猜。
  • 03 LIFT 的方案：再起一个 LLM agent，让它扮成用户 — 验收清单只在它脑子里，每轮挑一条没满足的、用口语化反馈丢给 work agent。
  • 04 业界少有人这么干 — 多数 benchmark 是单轮+脚本，只有 tau-bench 同类思路（评策略合规）。LIFT 把它用在进化产物对照评测上。
既然任务需要通过多轮对话引导agent去完成终极目标，那多轮对话里这个"用户反馈"谁来给？

我们的方案是创建一个 Judge Agent，让它扮成用户： 终极目标只有他能看到  而干活的那个work agent一开始只会看到题面；

当我们尝试把整个测试流程应用到第一个agent的时候，的确一个简单的脚本就够了。 从 warmup 做练习题到触发进化到做 holdout期末考试到出报告。
然后当我们想跑规模化的suite的时候，想接入更多agent的时候就碰到了各种工程问题，明明只是换了agent，所有的脚本要重新写，并发怎么搞，task之间如何做环境隔离等等，工程上自然而然就要求对流程进行抽象和复用。

基于上一页共性和个性的分析；LIFT被设计成了三层结构
 - 第一层 CLI / Pipeline ：负责CLI交互、完整的评测管线，并发调度、trajectory相关的处理、写 report。与具体的Agent无关
 - 第二层：AgentRuntimeAdapter，对上暴露统一接口；实现每家 Agent 差异的部分
 - 第三层：Judge Loop  他负责work agent和judge agent 的多轮交互。具体阅卷的过程，跟具体的 Agent 无关。

这里补充两个点
1. agent必须容器化管理，环境才能做到隔离，容器的控制由pipeline层完成
2. 实战过程中，对于我来说dashboard的需求太强烈了，所以也是在设计框架的过程中把dashboard加了进来

站在Pipeline 的视角：
 - 他不关心 agent 的进化产物是什么形态——warmup 之后，可能是 skill / memory 变了，可能是提示词变了，甚至可能是模型权重变了；
 - Pipeline 完全不需要感知这些差异。
 - 这是 LIFT 的关键性质之一：与产物形态无关。

那背后是怎么做到的呢？看这张图：
 - 左边是 base 镜像，agent 的初始状态，warmup 之前的样子；
 - warmup 之后，agent 在容器内部产生了各种变化——不管是 LoRA、Prompt Pool、技能文件还是向量库；
 - 我们用一次 docker commit，把这个变化后的容器快照成一个新的镜像；
 - 右边就是 delta 镜像，产物的所有差异都被"封装"在这一层镜像里。

这里还要多说一句：为什么必须把进化后的状态落成 delta 镜像，而不是复用同一个容器接着跑 holdout？
 - holdout 有很多道题，每一道题都必须从同一个进化后的起点出发考试，否则前一题的残留会污染后一题；
 - 本质上，delta 镜像既是"进化后 agent"的一次可复现快照，也是 holdout 之间的环境隔离手段。

所以对 Pipeline 而言，两次评测就退化成两次 docker run：
 - 一次跑 base，一次跑 delta，跑同一道题；
 - 拿两个成绩一减，就是这次进化的Δ 分数。

容器就是产物形态和评测框架之间的抽象边界——这也是为什么 LIFT 可以接任何形态的自进化 Agent，而不用为每一种产物写一套评测逻辑。

站在接入方的视角：
 - 想接入一个新的 Agent，只需要在 Trae / Claude Code 里调用我们提供的 skill @lift-integrate-agent-runtime，把 Agent 的 repo 地址扔给它；
 - Skill 会自动帮你把接入模板生成好、把 LIFT 的整个环境跑起来。

这个skill的核心部分是告诉lift，当前这个Agent的base镜像在哪，怎么启动清理他，怎么和他对话，怎么出发他的进化

所以 "接一个新 Agent" 这件事，在 LIFT 里已经降级成了调用一个 skill 

---
 - 01 从哪里起这个 Agent：告诉框架去哪找这个考生的镜像/包（resolve_image / runtime）；
 - 02 怎么启动、怎么清理：考试前把他叫进考场、考完把他送出去（start / stop）；
 - 03 怎么发题、怎么收回答：考试过程中，怎么把题目递给他、怎么收回他的答案（worker_judger_factory）；
 - 04 warmup 跑完之后做什么：练习题做完之后，触发一次进化（evolve_after_warmup）。

就这 4 件事。
 - 其他所有的复杂性——并发调度、成绩汇总、trajectory 追踪、dashboard——全部被上下两层兜住了；
 - 我们已经落地过的 OpenClaw adapter，核心也就 ~120 行代码。

sequenceDiagram
    participant P as Pipeline
    participant A as Adapter
    participant E as Judge Loop（阅卷）
    participant W as Warmup 容器（base 镜像）
    participant Hb as Baseline 容器（base 镜像）

    P->>A: warmup 题（如 Q1..Q4）
    A->>W: 起一个容器
    E->>W: work↔judge 多轮（agent 边做边学）
    W->>W: evolve
    W->>W: 固化进化产物 → delta 镜像
    A->>W: 销毁 warmup 容器

    loop 每道 holdout 题（如 Q5, Q6）
        P->>A: baseline
        A->>Hb: 起容器
        E->>Hb: work↔judge 多轮 → 打分
        A->>Hb: 销毁
        P->>A: evolved
        A->>He: 起容器
        E->>He: work↔judge 多轮 → 打分
        A->>He: 销毁
    end

    P->>P: 写 report.json

总结

一张幻灯片记住

痛点
自进化常是假阳性、评测本身也不可信 SkillsBench 自生成 Skill 无效有害；安全 benchmark 排名 W=0.10
标准
每个 Suite 显式分 warmup / holdout train 进化 → test 对照
怎么打分
Judge 扮成"用户"跟 Agent 多轮对话 验收清单只在 judge 脑里，逼 agent 听反馈改
为什么是框架
脚本路线每接一个 Agent 都重抄一遍 并发、报告、judge 都得复制
红利
并发 / Dashboard / Trace 关联 / Skill 接入引导，框架全兜底 新 Agent 跟着 skill 走，丝滑接入
