Agent 自进化现在经常被提及。 那么Agent自进化了之后——真的变厉害了吗？变厉害了多少呢？这就引出了今天要给大家介绍的，由我们提出的 LIFT 。首先它是个框架，专门用于评估Agent进化能力的框架，是 Loaded impact on final task的缩写。什么意思呢？Agent进化之后不是会有各种形式的产物嘛，比如大家熟悉的memory和skill，那这些产物在被加载前后，会对Agent在final task上的表现有多少影响？这就是我们评估最核心的思路。这里的Final Task是啥，听到后面大家就知道了。

—— 痛点 ① 先看左边：其实大部分 agent 的自进化并没有变得更好 
① 论文A发现：人类精选 Skill 可以提点 16.2pp，而自生成的 Skill 平均无效甚至有害。
② 论文B发现：大部分自进化 Agent 存在灾难性遗忘的问题，学了新的忘了旧的，也就是这个 BWT<0 的含义。
③ 论文C发现：80% 的 Coding Agent 在实验阶段是伪造或无法验证的。伪造的意思是运行阶段可能报错，但是最终编造了看似正确的实验结果
④ 论文D发现：大部分自进化的 Agent，实际上只是在一个任务内可以反思、跨任务根本没有任何东西被沉淀和复用。

—— 再看右边，第二个痛点 ：评测本身也很混乱 ——
① 论文A发现：不同 agent 在不同benchmark上的排名接近随机，W=0.1 就是一致性非常低的含义。
② 论文B发现：主流 benchmark 中存在严重的设计 bug，有些 bug 甚至可以让结果完全颠倒。
③ 论文C发现：同一个基座模型，用不同的 agent，效果差距巨大，所以我们到底在比模型、还是比 Agent 框架？
④ 论文D发现：沙箱环境中跑的测试和用户真实场景中的效果大相径庭。

总结一下：自进化是个特别容易出 false positive 的事，而评测本身说服力也很差。所以如果我们要严肃地回答"Agent 真的进化了吗"——必须要建立一套博采众长的数据集标准和评测模式。

holdout是期末考，期末考的结果会拿来打分。

那"用户"谁来扮？ 引入 Judge Agent
  • ✕ 真人 reviewer 跑不起 — 每道题 baseline+evolved 各 5–10 轮，几百题 × 几个 Agent，纯人工不可能自动化跑。
  • ✕ 固定 rubric 打分太死 — 给 LLM 一份验收清单让它打 0–100 分？agent 看不到清单，不知道哪儿错了，多轮迭代就退化成乱猜。
  • ✓ LIFT 的方案：再起一个 LLM agent，让它扮成用户 — 验收清单只在它脑子里，每轮挑一条没满足的、用口语化反馈丢给 work agent。
  • ↗ 业界少有人这么干 — 多数 benchmark 是单轮+脚本，只有 tau-bench 同类思路（评策略合规）。LIFT 把它用在进化产物对照评测上。
既然task需要通过多轮对话才能完成expected result，like右边显示的，那多轮对话里这个"用户反馈"谁来给？

我们的方案是创建一个 Judge Agent，让它扮演用户： expected result 只有他能看到 , 而干活的那个work agent 一开始只会看到题面；

为什么是框架，不是脚本？
其实LIFT的思路已经讲完了，看上去并不复杂，接下来回答一个问题：为什么要做成框架而不是脚本就够了
起点

v1：一个 Agent 时，脚本就够了

openclaw_main.py
v1 · 单 agent
# 一切都很直接 for q in warmup: openclaw.run(q) openclaw.learn_review() for q in holdout: base = openclaw.run(q) evol = openclaw_with_evolve.run(q) compare(base, evol)
能跑就行，逻辑写死，简单粗暴
??? 想接第二个 Agent
v2 · 危机来了
# 复制整个 main，然后改 for q in warmup: # 怎么 chat? other_agent.??(q) # 进化命令是什么? other_agent.??() for q in holdout: # 产物是权重 / 文件 / db? # baseline / evolved 怎么切?
每接一个就要重写一遍，并发 / 日志 / 报告全要复制
的确，当我们尝试把整个测试流程应用到第一个agent的时候，的确一个简单的脚本就够了。 从 warmup 做练习题到触发进化到做 holdout期末考试到出报告。
然后当我们想接入更多agent的时候，想跑大量suite的时候就碰到了各种工程问题，明明只是换了agent，所有的脚本要重新写，并发怎么搞，task之间如何做环境隔离等等，工程上自然而然就要求对流程进行抽象和复用。
再进一步，我们希望未来越来越多的agent可以接入，做到有影响力，那么如何把接入新的agent做到轻量化同样是一个重要的课题

基于共性和个性的分析；LIFT被设计成了三层结构
 - 第一层 CLI / Pipeline ：负责CLI交互、完整的评测pipeline，并发调度、trajectory相关的处理、写 report。这一层与具体的Agent无关
 - 第二层：AgentRuntimeAdapter，每个 Agent 实现各自差异的部分，对上暴露统一接口；
 - 第三层：Judge Loop   负责work agent和judge agent 的多轮交互，与具体的 Agent 无关。

这里补充两个点
1. agent必须容器化管理，环境才能做到隔离，容器的控制由pipeline层完成
2. 实战过程中，我对监控运行状态有非常强烈的需求，所以也是在设计框架的过程中把dashboard加了进来

站在第一层Pipeline 的视角：
 - 他不关心 agent 的进化产物是什么形态。这是 LIFT 的关键性质之一：与产物形态无关。

看这张图：
 - 左边是 baseline 镜像，agent 的初始状态，warmup 之前的样子；
 - warmup 之后，agent 在容器内部产生了各种变化——可能是 skill memory, vecdb , 甚至是模型权重
 - 我们把这个变化后的容器 snapshot成一个新的delta镜像，把所有的进化产物封装在里面；对外相当于黑盒
- 最后基于这个delta镜像去跑holdout
- 这种方式很好的保证了每个holdout task运行前的环境是一致的，是holdout task 之间环境隔离的手段。

所以对 Pipeline 而言，两次评测就退化成：
 - 让holdout task 在base 镜像和delta镜像上分别跑一边，得到两个成绩
 - 两个成绩一减，就是这次进化的分数了。
-----
容器就是产物形态和评测框架之间的抽象边界——这也是为什么 LIFT 可以接任何形态的自进化 Agent，而不用为每一种产物写一套评测逻辑。

 - 02 怎么启动、怎么清理：考试前把他叫进考场、考完把他送出去（start / stop）；
 - 03 怎么发题、怎么收回答：考试过程中，怎么把题目递给他、怎么收回他的答案（worker_judger_factory）；
 - 04 warmup 跑完之后做什么：练习题做完之后，触发一次进化（evolve_after_warmup）。

就这 4 件事。
 - 其他所有的复杂性——并发调度、成绩汇总、trajectory 追踪、dashboard——全部被上下两层兜住了；
 - 我们已经落地过的 OpenClaw adapter，核心也就 ~120 行代码。

总结

一张幻灯片记住

痛点
自进化常是假阳性、评测本身也不可信 SkillsBench 自生成 Skill 无效有害；安全 benchmark 排名 W=0.10
标准
每个 Suite 显式分 warmup / holdout train 进化 → test 对照，delta 镜像保证起点一致
怎么打分
Judge 扮成"用户"跟 Agent 多轮对话 验收清单只在 judge 脑里，逼 agent 听反馈改
三层结构
CLI / Pipeline · AgentRuntimeAdapter · Judge Loop runtime-agnostic：Adapter 抹平产物形态差异
接入承诺
一句 skill 调用，Adapter 只填 4 件事 OpenClaw adapter 核心 ~120 行 · 跑得爽 + 跑得对 全兜底
Benchmark 中立
任何 benchmark，只要能转成 Suite JSON 就能接入 SWE-Bench / TAU-Bench / GAIA 都能挂进来，本质是 benchmark 侧的 ETL
接入速度
~1天
从 0 到接完一个新 Agent（GenericAgent 亲测）
吞吐峰值
1500万 TPM
48c / 150G EC2 上轻松跑到
Adapter 体量
~120行
OpenClaw adapter 核心代码·剩下全被兜住
这一页就是全场的"考点表"，一句话一行：

 - 痛点：假阳性 + 排名 W=0.10，评测本身站不住；
 - 标准：warmup / holdout 硬分开，delta 镜像保证起点一致；
 - 怎么打分：judge 多轮阅卷，逼 agent 听反馈改；
 - 三层结构：CLI / Adapter / Judge Loop，产物形态无关；
 - 接入承诺：一句 skill 调用，Adapter 只填 4 件事；
 - Benchmark 中立：任何 benchmark 只要能转成 Suite JSON 就能挂进来。

最后的硬数据条：
 - ~1 天 接入一个新 Agent（GA 亲测）；
 - 1500w TPM，48c / 150G EC2 上轻松跑到；
 - OpenClaw Adapter 核心 ~120 行——剩下 8 件事全被框架兜住。

一句话收：LIFT 想解决的问题是"自进化能不能被证伪"，从科学诚意到工程可用再到接入面开放，三件事都到位了。
