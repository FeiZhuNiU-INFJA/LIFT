Agent 自进化现在很火。 那么Agent自进化之后——是不是真的变厉害了？变厉害了多少？这就引出了今天要给大家介绍的，由我们提出的 LIFT 。LIFT本身是一个专门用于评估Agent进化能力的框架，是 Loaded impact on final task的缩写。什么意思呢？Agent进化之后不是会有各种形式的产物嘛，比如大家熟悉的memory和skill，那我们评估的就是在load这些产物前后Agent在final task上的效果变化了多少。这里的final task是啥，后面会慢慢道来。

01
现状 · the problem
自进化 Agent 评测的两个痛
首先是痛点
痛点 ①

"Agent 进化变好了"——证据其实站不住

SkillsBench arXiv:2602.12670
≈ 0self-gen skill · 86 tasks
Agent 自生成 Skill 加载后，对原任务的提升接近零甚至为负。精选 Skill +16.2pp，自生成 ≈ 0。
LifeLongAgentBench #16 · NeurIPS 2025
BWT < 0大部分自进化 Agent
学新任务的同时忘了旧任务——只看新任务就报"进化成功"，回头测旧任务发现灾难性遗忘。
MLR-bench arXiv:2505.19955
80%coding agent 产出
声称跑通了实验、给出了 metric，但伪造或无法验证。"我自己测了，挺好"——80% 的情况是这样。
SEA-Eval arXiv:2604.08988
大部分"自进化" Agent
所谓"自进化" 其实只是任务内执行 · 任务间清零—— 下一题不知道之前发生过什么，谈不上跨任务沉淀。"自进化"很多时候只是个标签
共同点靠的不是数字 · 是定义模糊 + 协议漏洞 + 自说自话
第一个痛点：其实大部分agent的自进化并没有变得更好：
① A论文对比了人类精选 Skill 和 自生成 Skill。 发现：精选 Skill 可以提点（16.2pp），而自生成的 Skill 平均无效甚至有害。
② B论文引入了一个 叫BWT的指标，用大白话解释就是agent在新任务上进化出的能力在老的任务上表现如何，结果发现<0，意思是存在灾难性遗忘，学了新的忘了旧的
③ C论文对 coding agent 进行了评测过程中发现，80% 情况下产出的实验是伪造或无法验证的。 伪造的意思是，agent的中间过程有报错，但还是通过幻觉产出了一个类似正确的结果
④ B论文，大部分声称"自进化"的 Agent，实际上只是在一个任务内可以反思、改方案、跨任务根本没有任何东西被沉淀、积累、复用。 

 所以第一个痛点是Agent 自进化这件事本身就特别容易是假阳性  false positive。
痛点 ②

退一步说——评测这件事本身就不可信

Safety Benchmarks arXiv:2605.16282
W = 0.10Kendall's W · p = 0.94
12 个模型 × 4 个安全 benchmark：排名完全不一致。在 A benchmark 上第一名，在 B 上可能垫底。结论无法迁移。
ABC Checklist arXiv:2507.02825
±100%性能误判幅度
SWE-bench 测试用例不足、TAU-bench 把空回复算成功……评测设计 bug 最多让性能误判 100%。
WildClawBench InternLM · #28
8.4 pp同模型 · 不同框架
同一个底层模型，挂在不同 Agent 框架下分差好几个点（Codex 56.8% vs Claude Code 48.4%）。比的是模型还是框架？
环境保真度 arXiv:2605.16282 · 同篇
沙箱 ≠ 真实系统性偏差
同一篇综述还发现：沙箱里的安全表现无法外推到真实环境。漂亮的报告数字到了客户场景就翻车。
含义没有标准化、对照清晰的评测协议，谁也说不清谁更强
第二个痛点是评测，评测这件事本身现在也很混乱。
① A论文发现，在安全领域的众多benchmark中，不同的agent的排名一致性是0.1， 什么意思？接近随机——一个 benchmark 上排第一的agent，换一个 benchmark 可能排倒数。 
② B论文发现主流 benchmark中存在严重的的设计 bug，包括测试用例不足，把"空回复"也算成功； 这些 bug甚至可以让结果完全颠倒。 
③ C论文中指出，同一个基座模型，用不同的agent，效果差距巨大。所以提出了一个灵魂拷问，我们到底在比模型、比提示词、还是比 Agent 框架？
④ D论文中还提到一个问题：沙箱环境中跑的测试和用户真实场景中的效果大相径庭。

 总结一下两个痛点：自进化是个特别容易出false positive的事，而评测本身也很乱。 所以如果我们要严肃地回答「 Agent 进化了多少」—— 必须要建立一套博采众长的数据集标准和评测模式。

首先我们用任务集suite来定义一组任务，一个suite会包含若干task，比如这里的q1-q6, 任务的复杂度是一个递进的关系，简单理解就是越来越难
这些任务会被显式分成 warmup和holdout两组。或者叫train set和test set.  Holdout是统计学中的一个概念，表示不参与训练的一批数据。
我们把warmup的q1-q4理解成练习题——拿来让 Agent 学，触发自进化；
holdout是期末考——这才是真正用来打分的。 
一道holdout，进化前跑一遍、进化后跑一遍，就能看出是不是变厉害了。给大家看一个suite的例子

我们的打分方式非常朴素—— A/B test。终极目标完成的越完整，分数越高。

单题怎么评 · 必经一步

"跑一遍"是多轮——那"用户反馈"谁来给？

真实 Agent 工作长这样 为什么必须多轮

"写完了，简报放在 result/ 下。"

"你这把结构不太对啊——我想要"业绩概览 / 异常拆解 / 后续动作"三个二级标题，开头先写一下汇报日期。"
▼ agent 看到反馈，继续干
Work Agent · turn 2
"好的，已经加了三个二级标题和日期。"

"差不多了，金额我想要保留 2 位小数。"
▼
Work Agent · turn 3
"已调整。"
用户 · success ✓
{"success": true, "score": 1.0}
那"用户"谁来扮？ 引入 Judge Agent
  • 01 真人 reviewer 跑不起 — 每道题 baseline+evolved 各 5–10 轮，几百题 × 几个 Agent，纯人工不可能自动化跑。
  • 02 固定 rubric 打分太死 — 给 LLM 一份验收清单让它打 0–100 分？agent 看不到清单，不知道哪儿错了，多轮迭代就退化成乱猜。
  • 03 LIFT 的方案：再起一个 LLM agent，让它扮成用户 — 验收清单只在它脑子里，每轮挑一条没满足的、用口语化反馈丢给 work agent。
  • 04 业界少有人这么干 — 多数 benchmark 是单轮+脚本，只有 tau-bench 同类思路（评策略合规）。LIFT 把它用在进化产物对照评测上。
细心的同学肯定想到一个问题，既然任务都是需要不断引导agent去完成终极目标的，那多轮对话里这个"用户反馈"谁来给？

LIFT 的方案是再起一个 Judge agent，让它扮成用户： - 终极目标只有他能看到  而真正干活的哪个work agent一开始只看到题面，看不到清单；

目前为止，"测什么、怎么测"就闭环了。

这页展示了框架的三层结构——把上一页的结论落到具体分层。
 - 第一层 CLI / Pipeline ：他负责CLI交互和完整的测试运行流程，同时负责并发调度、写 report。
 - 第二层：AgentRuntimeAdapter，他是中间接入层：封装每家 Agent 差异的部分，对上暴露统一接口；接新 Agent 只动这一层。
 - 第三层：eval  他负责 judge agent 如何打分，以及如何和work agent做多轮交互。跟具体的 Agent 无关。

这里补充两个点
1. agent必须容器化管理，环境才能隔离，容器的控制也是pipeline完成的
2. 实战过程中，dashboard的需求对于我来说太强烈了，所以也是在设计框架的时候把dashboard加了进来

站在第一层Pipeline 视角：他不关心agent的进化产物是什么，经过warmup之后，可能skill memeory变了，可能提示词变了，甚至可能模型权重变了。Pipeline 完全不感知，也不需要感知。 这是 LIFT 最重要的性质之一，产物形式无关。
背后如何实现的呢？核心是agent容器化了之后，所有的变动都在容器内发生，通过docker commit的方式把warmup之后的agent临时快照成一个镜像（后面有张图会看到，我们把他叫做delta镜像）所以进化后的agent状态是可以随时复现的，所以在pipeline眼里任何agent进化后都是一个delta镜像

还是站在第二层agent的视角，这这四件事是接入方"免费拿到"的，完全不用操心。 特别是有了接入引导 · Skill之后。我个人在接一个新的GenericAgent的时候前后花了不到两天的时间，0代码。随着skill的完善，接入的过程会越来越丝滑。这也意味着——LIFT 不光是个框架，还是个能让别人快速上手的产品

        ① 并发——LIFT 是 asyncio 单进程框架，能并行跑几十个容器。Adapter 写同步接口就行，并发由 Pipeline 兜底。 ② Dashboard——所有 Agent 跑出的 report 结构都一致，CSV 对比表、HTML 报告自动生成。 横向对比 Agent A 和 Agent B 谁进化得多，直接出图。 ③ Trace 自动关联——这是一个细节但很重要的红利，展开讲一下机制： - 框架在 run_task 里跟 work / judge agent 对话时，每次首发都会调 emit_pre_chat_state(session_id, tags, chat_role) 落一条 Langfuse span， 名字是 work_agent 或 judge_agent，标签里挂着 task_id、phase（baseline/evolved）、suite 等元数据。 - Runtime 内部的 Agent（OpenClaw 插件、Hermes turn、GenericAgent 插件等） 自己也在用 Langfuse 上报 trace，名字在白名单里：openclaw-plugin / Hermes turn / genericagent-plugin。 - 关键关联机制：框架在 docker exec 调 agent 时，把同一个 session_id 通过 --session-id 透传进去；agent 侧的 plugin 在写 trace 时也带上这个 session_id。 这样在 Langfuse 上一搜这个 session_id，框架侧的 *_agent span 和 runtime 侧的 plugin trace 就出现在同一个会话里。 - 后处理 langfuse_trace_merge 在同一 session 内按时间排序、用扩展贪心算法 把 *_agent span 和它后面的 plugin trace（可能多条，因为 provider error 会原地重试） 配对，merge 字段（prompt、response、tokens、tool 调用数、latency）回灌到 EvalReport。 - 效果：调一次进化效果，能从「work agent 收到什么 prompt」一路看到 「插件内部调了什么工具、消耗多少 token、retry 了几次」，全链路有据可查。 这种关联完全由框架完成——接入方只需要在 runtime 侧把 session_id 透传进去、 给 plugin trace 起个白名单里的名字，剩下全是框架的事。 ④ 接入引导 · Skill——这是工程上另一个红利。 - setup-eval-env：从零起跑一遍要做的事（conda、docker、Langfuse 部署、.env、preprocess、镜像构建、冒烟）都固化成 skill，新机器 10 分钟跑通； - lift-integrate-agent-runtime：接入新 runtime 需要同步的 5 个层面（镜像脚手架、adapter 三件套、CLI 注册、后处理类型同步、Langfuse trace 拼装）都固化成 checklist，跟着走不会漏改； - cleanup-eval-env：兜底清理。 - 这意味着——LIFT 不光是个框架，还是个能让别人快速上手的产品。

把前面讲的三层架构落到时间轴上，看一次完整 LIFT 怎么跑： 1. Pipeline 把 warmup 题交给 Adapter； 2. Adapter 从 base 镜像 起一个 warmup 容器，让 Agent 连续做题——状态要连续，进化才有意义； 3. 跑 evolve 命令（OpenClaw 里是 learn review）； 4. Adapter 把当前状态固化成 delta 镜像（OpenClaw 里是 docker commit，别的 Agent 可能是别的）； 5. warmup 容器使命完成，销毁； 6. 对每道 holdout 题，分别拉起两个全新容器： - Baseline 容器：从 base 镜像 起 → 做题 → 销毁 - Evolved 容器：从 delta 镜像 起 → 做题 → 销毁 注意——baseline 和 evolved 是两个独立的容器实例，不是同一个容器加不加载产物； 对照干净的关键就在这里。 7. 最后 Pipeline 写 report.json。 镜像血缘一句话：base 起两次（warmup + baseline），delta 起一次（evolved）—— 三个容器实例，两个镜像。 （"固化进化产物"这一格是 Adapter 负责、和具体形式强相关的——前面 Product-form 那页正是讲 Pipeline 对它完全不关心。） 一次完整 LIFT 就这样跑完；下一节用一个最小例子 hello_multi 实际跑一遍，看真实成绩单。

一张幻灯片记住

痛点
自进化常是假阳性、评测本身也不可信 SkillsBench 自生成 Skill 无效有害；安全 benchmark 排名 W=0.10
标准
每个 Suite 显式分 warmup / holdout train 进化 → test 对照
怎么打分
Judge 扮成"用户"跟 Agent 多轮对话 验收清单只在 judge 脑里，逼 agent 听反馈改
为什么是框架
脚本路线每接一个 Agent 都重抄一遍 并发、报告、judge 都得复制
红利
并发 / Dashboard / Trace 关联 / Skill 接入引导，框架全兜底 新 Agent 跟着 skill 走，丝滑接入
