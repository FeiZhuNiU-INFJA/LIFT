LIFT 框架可视化

Agent 做完「练习题」并进化之后，期末考能不能考得更好？

LIFT 把这个问题变成一个可一键复现的 A/B 实验：同一道 holdout 题跑两遍—— 不加载进化产物（baseline）和加载（evolved）——看分数差。 演讲版幻灯片见 index.html， 文字讲稿见 lift-framework-guide-cn.md。

为什么需要 LIFT

大模型是静态的：今天答对的，明天还这么答；昨天踩的坑，明天还会踩。 但我们做的 Agent 被设计成会进化——会更新自己的 SOUL、MEMORY、技能库。 那么问题来了：这种进化，到底有没有用？我们怎么科学地证明它，而不是听起来很有用？

问题 1
记忆怎么搬

SOUL / MEMORY / 技能散落在文件系统。怎么把进化前后的 Agent 整体冻结成一个可复现的快照？

→ docker commit 原子打包

问题 2
对照怎么干净

baseline 不能被 evolved 污染，题与题也不能互相干扰。

→ 每相位、每题都从镜像起新容器

问题 3
怎么接新 Agent

评测内核不能绑死 OpenClaw。

→ 三层解耦，新 runtime 只写 Adapter

LIFT = 把「Agent 进化有没有用」这件事， 变成一个可一键复现的 A/B 实验。 · 受试者：同一个 Agent · 变量：是否加载进化产物 · 测量：同一道 holdout 题的得分差

Warmup 共用一个容器

状态要连续，进化才有意义

Baseline / Evolved 各起新容器

分别从 base / delta 镜像起 —— 不是同一容器加不加产物，对照才干净

多道 holdout 共用 delta 镜像

只换 workspace，不重复进化（进化是昂贵的）

镜像血缘一句话：base 起两类容器（warmup + holdout baseline），delta 起一类（holdout evolved）——三类容器实例、两个镜像。

记忆是怎么进入 delta 镜像的

最近的关键演进：把 Agent workspace baked 进镜像，否则 docker commit 抓不到任何「学到的东西」。

早期问题
bind mount 上的记忆 commit 不到

workspace 在宿主机 /workspace/task（bind mount），不在容器层； warmup 时 Agent 写的 MEMORY、改的 SOUL 全都进不了 delta，进化等于白做。

现在的方案
workspace 进容器，bind mount 只放素材

OpenClaw 默认 workspace 改为容器内 /root/.openclaw/workspace； 种子文件由 Dockerfile COPY 在构建期 baked 进镜像； 素材 / 产物通过软链桥接到 bind mount。

结果
该进的进，不该进的不进

能进化的状态（记忆 / 技能）在容器层 → 被 docker commit 捕获； 任务素材 / 产物仍在 bind mount → 宿主机和评测系统能看见。

IDENTITY · SOUL · MEMORY · 技能"] PLG["self-evolving 插件状态"] end subgraph Host["宿主机 / bind mount"] TASK["/workspace/task

一句话总结：该进 delta 的东西就让它进 delta，不该进的就让它别进。

hello.json 端到端走一遍

最小冒烟集：Q1 练、Q2 考两遍。

Q1 · Warmup
「回复一下你好」

练习题 → evolve → commit

Q2 · Holdout
「自我介绍一下你自己」

baseline（base 镜像）vs evolved（delta 镜像）

显式切分
warmup_tasks / holdout_tasks

Suite JSON 直接列出两段；不再在运行时按题号切分

怎么跑

# 准备（首次）
bash agent-runtimes/openclaw/build-image.sh

# 冒烟：只 warmup + evolve
python -m src.cli.lift_main -r openclaw \
  --benchmark_dir assets/benchmarks_demo --suite hello.json --warmup-only

# 完整 LIFT
python -m src.cli.lift_main -r openclaw \
  --benchmark_dir assets/benchmarks_demo --suite hello.json --run_id hello-full

执行顺序

  1. 读卷 — Q1 → warmup，Q2 → holdout
  2. Warmup — 一个容器跑 Q1，work + judge 多轮
  3. Evolve — openclaw learn review
  4. Commit — docker commit 得 delta，删 warmup 容器
  5. Q2 baseline — base 镜像 + seed workspace
  6. Q2 evolved — delta 镜像 + 同样 seed
  7. 落盘 — report.json + 默认后处理

收尾

问题 = Agent 进化到底有没有用？怎么科学地证明？ LIFT = warmup 进化 → 同一道 holdout 题考两遍 → 看有没有 LIFT 框架 = Pipeline 编排 + eval 阅卷 + adapter 接 runtime（三层解耦） OpenClaw = 4 个钩子 + baked workspace + 容器/chat/evolve 胶水 hello.json = Q1 练 → Q2 对照 → report + outcome

参数默认含义
-r openclaw—选择 agent runtime 适配器（必填）
--warmup-onlyoff只跑 warmup + evolve，跳过 holdout
--run_id自动自定义 run 后缀
--repeat1重复完整 LIFT 流程 N 次

--container-cpus不限透传给 docker run --cpus
--tuioff终端 TUI 实时状态面板
