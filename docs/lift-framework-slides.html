开场。 我们在做会自我进化的 Agent。但「进化」这个词在业界一直很模糊——说它有用，但用什么标准衡量？ 今天讲的 LIFT 框架，就是把这件事从「感觉」变成可一键复现的数字。 分三段：先讲现状的痛点、再讲我们的标准和工程，最后讲为什么做成框架而不是脚本。
01
现状 · the problem
自进化 Agent 评测的两个痛
第一段。先不讲我们做了什么，先讲业界这件事现在是怎么干的。 两个核心痛点，都是过去一年学术界自己摸出来、有量化证据的： - 「Agent 进化变好了」常常是错觉——自生成产物平均无效甚至有害，看似变好可能是评测协议在骗你； - 退一步说，评测这件事本身就不可信——同一个 Agent 不同 benchmark 排名完全不一样。 这两个痛点是「为什么需要 LIFT」最直接的回答。

看一眼业界现状—— 过去一年「自进化 Agent」特别热，每个项目都说自己「学会了」、「进化了」、「变更聪明了」。 但 2025 年学术界做了几篇硬碰硬的实证研究，结论挺扎心： ① SkillsBench（arXiv:2602.12670）在 86 个任务上系统对比了"无 Skill / 精选 Skill / 自生成 Skill"三种条件。 结果：**精选 Skill 提升明显（+16.2pp），但 Agent 自己生成的 Skill 平均无效甚至有害。** 换句话说——「Agent 沉淀技能让自己变强」这件事，目前最大规模的实测说：基本没发生。 ② LifeLongAgentBench 引入 FWT/BWT 这种学习曲线指标—— 发现大部分自进化 Agent 存在显著的**灾难性遗忘**：学新任务的同时忘了旧任务。 你只测新任务，看着进化了，回头测旧任务就露馅。 ③ MLR-bench（NeurIPS 2025）评测 ML 研究型 coding agent—— **80% 情况下产出的实验是伪造或无法验证的**。 Agent 自己说「我跑了实验，效果很好」——80% 时候是不可信的。 这恰恰对应业界很多「我们让 Agent 学了一下，看挺好」的报告。 ④ 这个最戳——我们自己调研时发现的： 常见的评测协议是 "跑 Q1-Q5 → 触发学习 → 再跑 Q1-Q5"。 看起来 Run 2 分数提升了就是进化了。其实不是——Agent 可能只是把 Q1-Q4 的答案搬运到 Q5。 真正的进化应该是「学了 Q1-Q3，能解从未见过的 Q4/Q5」。 ——这条直接铺垫了我们 Suite 里 warmup_tasks / holdout_tasks 显式分离的设计。 所以第一个痛点不是「业界小作坊不严谨」，而是**自进化 Agent 这件事本身就特别容易出假阳性**： 协议有漏洞、产物可能有害、Agent 自己评自己不可靠。这是为什么需要严格的对照实验框架。

第二个痛点退一步看——就算抛开"进化有没有用"这件事， **评测这件事本身现在也很混乱**。同一个 Agent，换个 benchmark 就不一样的结论。 ① 最硬的证据是 arXiv:2605.16282 这篇综述—— 编目了 40 个 Agent 安全 benchmark，挑 12 个模型 × 4 个主流 benchmark × 3 类风险， 跑 Kendall's W 一致性分析。结果：**W = 0.10, p = 0.94**。 什么意思？接近随机——一个 benchmark 上排第一的模型，换一个 benchmark 可能排倒数。 这告诉我们：单个 benchmark 的"排名"几乎没有迁移价值。 ② ABC Checklist 是 NeurIPS 2025 的论文—— 系统性地审计了一批主流 benchmark，发现常见的设计 bug： - SWE-bench Verified 测试用例不足； - TAU-bench 把"空回复"也算成功； 这些 bug 可以让性能**被误判 100%（相对值）**。 换句话说，你看到的 "GPT-5 比 Claude 高 30%"——可能只是 benchmark 设计的副产品。 ③ WildClawBench——同一个底层模型， 挂在 Codex CLI 下是 56.8%，挂在 Claude Code 下是 48.4%。 我们到底在比模型、比 prompt、还是比 Agent 框架？ ④ 还有环境保真度——沙箱里跑 90% 安全率，到真实环境就 60%。 **总结这两个痛点**：自进化是个特别容易出假阳性的事，而评测本身也很乱。 所以如果我们要严肃地回答「我们的 Agent 进化了多少」—— 必须建立一套清晰、对照严格、可复现的评测协议。这就是 LIFT 在做的事。

先立一套数据集标准
既然外面没有，我们就自己立一套。 数据集标准是「能不能测出进化前后差距」这件事的前提。后面工程上的设计都是为了让这套标准落地。

关键设计就一条：**每个 Suite 都显式分 train（warmup）和 test（holdout）两堆题**。 train 是练习题——拿来让 Agent 学的，跑完触发进化； test 是期末考——这才是真正用来打分的。 而且 test 是精心设计的：75% 要求和 train 一致（考是否学到了），25% 是变体或矛盾要求（考会不会过拟合）。 有了这个切分，**我们才有资格谈「进化前后的对照」**——同一道 test 题，进化前跑一遍、进化后跑一遍，看分差。 数据集这块还有更多细节，构造方法、judge 多轮反馈等等，都在 suite_requirement.md 里，今天不展开——另一位同事后面会专门讲。

测量方法非常朴素——A/B 实验。 - 同一道 holdout 题，跑两遍：一遍不加载进化产物（baseline，对照组），一遍加载（evolved，实验组）。 - 分数差 = 这次进化的 LIFT。 受试者从用户换成了 Agent，但实验思路是经典的 A/B test。 但"跑一遍"具体是什么意思？真实 Agent 工作从来不是"给个 prompt → 一次写对"—— 客户会反复说"不对，再改改"。这一遍如果只测"agent 第一次写对没"，那根本测不出真本事。 下一页讲我们怎么处理"一遍"内部的多轮对话——这是 LIFT 另一个关键设计。
fig.05 · 单题怎么评 · 必经一步

那"用户"谁来扮？ 引入 Judge Agent
  • 01 真人 reviewer 跑不起 — 每道题 baseline+evolved 各 5–10 轮，几百题 × 几个 Agent，纯人工不可能自动化跑。
  • 02 固定 rubric 打分太死 — 给 LLM 一份验收清单让它打 0–100 分？agent 看不到清单，不知道哪儿错了，多轮迭代就退化成乱猜。
  • 03 LIFT 的方案：再起一个 LLM agent，让它扮成用户 — 验收清单只在它脑子里，每轮挑一条没满足的、用口语化反馈丢给 work agent。
  • 04 业界少有人这么干 — 多数 benchmark 是单轮+脚本，只有 tau-bench 同类思路（评策略合规）。LIFT 把它用在进化产物对照评测上。
上一页讲完"跑两遍 → 看分差"，听众会有个自然的疑问：**"跑一遍"到底是怎么跑的？** 看左边——真实 Agent 工作流不可能一次写对： - 用户先丢一句"帮我写个简报"； - Agent 交了，用户看完才想起"哦对了，结构要分三块"； - Agent 改了，用户又想起"金额保留 2 位"； - …直到用户满意。 所以"跑一遍"内部本身就是多轮 work↔reviewer 对话。如果只测"agent 第一次的产出"， 测不出 agent 听得懂反馈、能改对的真本事——而这正是 ToB 场景最重要的能力。 那问题来了：**多轮对话里这个"用户反馈"谁来给？** ① 真人不行——baseline+evolved 各 5–10 轮，几百题、多 Agent，**人力跑不起**。 ② 固定 rubric 打分也不行——给 LLM 一份 checklist 让它给分，agent 看不到 checklist， 不知道哪儿错了，多轮就退化成"再试一次"。 ③ LIFT 的答案是**再起一个 LLM agent，让它扮成用户**： - 验收清单**只在它脑子里**——work agent 一开始只看到题面，看不到清单； - 每轮挑一条最该改的，用口语化反馈丢给 work agent："哦对了，金额保留 2 位"； - 这不光让多轮跑得动，**还顺便模拟了真实 ToB 场景**——客户从来不会给你完美 spec。 ④ 业界对比一下： - SWE-bench、AgentBench、SkillsBench、MLR-bench 这些主流 benchmark 几乎都是 "单轮 + 确定性打分"——给一道题、跑一次、脚本判对错； - REAL 那种"112 多轮"指的是 agent 在网页上点很多次，**不是用户和 agent 来回对话**； - 真正用 LLM 模拟用户的就 tau-bench / tau2-bench——但它评的是策略合规 （"agent 退款前有没有验证身份"），不是产物质量在多轮迭代中的收敛。 - tau-bench 论文自己的结论是"最强模型在策略遵循上经常出错"——这本身就说明 多轮对话评测能挖出单轮挖不出的问题。 我们的 judge prompt 也仔细打磨过——要求它**说人话**：用第二人称、不要"当前未执行" 这种汇报体、每轮只挑一条最该改的、一两句话、不许罗列。这些是 prompt 工程的细节， 但让 judge 像个真实用户、而不是审计员，对评测信号的真实性影响很大。 讲完这一页，"测什么、怎么测"就闭环了。下面进入工程演化——这一切怎么落地跑起来。
03
工程演化 · the build
为什么是框架，不是脚本？
第三段，工程视角。 最容易引发共鸣的一段——很多同事都经历过类似的"脚本 → 框架"演化路径。 我们也是这样走过来的。
fig.06 · 起点

v1：一个 Agent 时，脚本就够了

openclaw_main.py
v1 · 单 agent
# 一切都很直接 for q in warmup: openclaw.run(q) openclaw.learn_review() for q in holdout: base = openclaw.run(q) evol = openclaw_with_evolve.run(q) compare(base, evol)
能跑就行，逻辑写死，简单粗暴
??? 想接第二个 Agent
v2 · 危机来了
# 复制整个 main，然后改 for q in warmup: # 怎么 chat? other_agent.??(q) # 进化命令是什么? other_agent.??() for q in holdout: # 产物是权重 / 文件 / db? # baseline / evolved 怎么切?
每接一个就要重写一遍，并发 / 日志 / 报告全要复制
工程演化第一步——这个项目第一版就是个脚本。 左边：那时候我们只有一个 Agent（OpenClaw），写个 for 循环就够了。 - 跑 warmup → 调一下 learn review → 跑 holdout 两次 → 对比。 - 一切硬编码，跑得通就行。**这种阶段没必要造框架，简单粗暴是优点**。 右边：危机什么时候来？想接第二个 Agent 的那一刻。 - 它怎么 chat？OpenClaw 走 `docker exec openclaw agent --json`，下一个 Agent 可能是个 HTTP 服务、可能是个 Python 库。 - 它的进化命令叫什么？不一定是 learn review。 - 它的进化产物是什么形态？可能是权重、可能是 prompt 池、可能是数据库。 - baseline / evolved 怎么切换？OpenClaw 是 docker commit，别人可能是换个配置文件。 如果你不抽象，你的选择是**复制整个 main**——然后并发逻辑、日志、报告输出、错误处理全部跟着复制。**这种重复正是「该上框架」的信号**。

如果继续走脚本路线，每接一个 Agent，至少这 4 块都要重复造： 1. **容器生命周期**——起、停、commit delta、出错时清理； 2. **并发调度**——多题并发跑、资源上限控制、一道题挂了不能拖死全场； 3. **Judge 多轮反馈**——work agent 答题、judge agent 评分、不通过给提示再来一轮； 4. **报告 / Dashboard**——CSV、HTML、和 Langfuse trace 的关联。 关键是：**这些事和具体 Agent 无关**，是评测本身的工程。但脚本化模式下，它们和 Agent 调用方式硬编码在一起，每个新 Agent 都得整套重抄一遍。 这就是我们要造框架的核心理由——不是为了优雅，是为了**别再写一遍**。

框架核心：三层解耦。 - **Pipeline** 只管编排——切题、跑 warmup / holdout、写 report；不知道 Docker 是什么、不知道哪家 Agent； - **eval** 只管单题阅卷——work + judge 多轮；不知道 Agent 跑在容器里还是裸进程； - **Adapter** 夹在中间，是**接新 Agent 唯一需要实现的层**。 这层 boundary 想清楚以后，前面那 4 块重复造的轮子全部留在 Pipeline 和 eval 里，新 Agent 只用写 Adapter。 这就是「评测」和「Agent」剥开的意思。

Adapter 接口收敛到 4 个钩子： ① 从哪里起这个 Agent —— 容器镜像、本地 binary、HTTP endpoint 都行； ② 怎么启动 / 清理； ③ 怎么向它发一道题、收回答 —— 这是 chat 接口的抽象； ④ warmup 跑完之后做什么进化 —— 没有就 no-op。 OpenClaw 的 adapter 实现里，**核心 adapter.py 大约 120 行**——把这 4 个钩子组装起来； 围绕它有 chat agent、容器执行、session 管理等支撑代码，整体也就接近 1k 行。 相比之下——并发调度、retry、judge 多轮、报告生成、Langfuse 关联这些事都不用接入方写一行。 这就是「框架红利」的具体含义。

这是 LIFT 最重要的性质——**产物形式无关**。 进化产物你想做成什么都行：LoRA 权重、prompt 池、技能文件、向量库…… Adapter 内部自己负责怎么把它「装载」回去—— - OpenClaw 走 `docker commit` 把整个容器层固化成镜像； - 改权重的 Agent 可以 `git checkout` 一个分支； - prompt 池可能就是 `cp config.json`； - 向量库可能是切换连接字符串。 但**框架完全不感知**。它只看一件事：同一道 holdout 题，evolved 分 vs baseline 分。 这就回到了开场说的——「不同 Agent 没法横向比」这个痛点，被框架的这个性质直接解掉了。

    end

    P->>P: 写 report.json
一次完整 LIFT 的时间线，从上往下讲： 1. Pipeline 把 warmup 题交给 Adapter； 2. Adapter 起一个容器，让 Agent 连续做题——这一步状态要连续，进化才有意义； 3. 跑 evolve 命令（OpenClaw 里是 learn review）； 4. Adapter 把当前状态固化成 delta（OpenClaw 里是 docker commit，别的 Agent 可能是别的）； 5. 对每道 holdout 题，分别跑 baseline 和 evolved 两个相位，每个相位起独立容器保证对照干净； 6. 最后 Pipeline 写 report.json。 注意"固化进化产物"这一格——是 Adapter 负责的、和具体形式相关；Pipeline 不关心。
fig.12 · 框架红利

Agent 接入方完全不用操心的事

⫶
并发调度
多 Suite 并行、多题并发、phase 并发都在 Pipeline 兜底；Adapter 只暴露同步接口，不用懂 asyncio
◧
统一 Dashboard
所有 Agent 的成绩单都长一样：
report.json + CSV 对比表 + HTML 可视化，横向对比直接做
◎
Trace 自动关联
框架 pre-chat span 与 runtime 内部 plugin trace 通过同一 session_id 串起来，work / judge / agent 内部工具调用 一条 trace 看到底
⌘
接入引导 · Skill
setup-eval-env 一键搭环境、lift-integrate-agent-runtime 把 5 个 touchpoint 固化成清单，新 runtime 接入 跟着走不漏改
这四件事，是接入方"免费拿到"的——脚本路线每个 Agent 都得重做一遍。 ① **并发**——LIFT 是 asyncio 单进程框架，能并行跑几十个容器。Adapter 写同步接口就行，并发由 Pipeline 兜底。 ② **Dashboard**——所有 Agent 跑出的 report 结构都一致，CSV 对比表、HTML 报告自动生成。 横向对比 Agent A 和 Agent B 谁进化得多，直接出图。 ③ **Trace 自动关联**——这是一个细节但很重要的红利，**展开讲一下机制**： - 框架在 `run_task` 里跟 work / judge agent 对话时，每次首发都会调 `emit_pre_chat_state(session_id, tags, chat_role)` 落一条 Langfuse span， 名字是 `work_agent` 或 `judge_agent`，标签里挂着 task_id、phase（baseline/evolved）、suite 等元数据。 - Runtime 内部的 Agent（OpenClaw 插件、Hermes turn、GenericAgent 插件等） 自己也在用 Langfuse 上报 trace，名字在白名单里：`openclaw-plugin` / `Hermes turn` / `genericagent-plugin`。 - **关键关联机制**：框架在 `docker exec` 调 agent 时，把**同一个 session_id** 通过 `--session-id ` 透传进去；agent 侧的 plugin 在写 trace 时也带上这个 session_id。 这样在 Langfuse 上一搜这个 session_id，框架侧的 `*_agent` span 和 runtime 侧的 plugin trace 就出现在同一个会话里。 - 后处理 `langfuse_trace_merge` 在同一 session 内按时间排序、用扩展贪心算法 把 `*_agent` span 和它后面的 plugin trace（可能多条，因为 provider error 会原地重试） 配对，merge 字段（prompt、response、tokens、tool 调用数、latency）回灌到 EvalReport。 - **效果**：调一次进化效果，能从「work agent 收到什么 prompt」一路看到 「插件内部调了什么工具、消耗多少 token、retry 了几次」，全链路有据可查。 这种关联**完全由框架完成**——接入方只需要在 runtime 侧把 session_id 透传进去、 给 plugin trace 起个白名单里的名字，剩下全是框架的事。 ④ **接入引导 · Skill**——这是工程上另一个红利。 - `setup-eval-env`：从零起跑一遍要做的事（conda、docker、Langfuse 部署、`.env`、preprocess、镜像构建、冒烟）都固化成 skill，**新机器 10 分钟跑通**； - `lift-integrate-agent-runtime`：接入新 runtime 需要同步的 **5 个层面**（镜像脚手架、adapter 三件套、CLI 注册、后处理类型同步、Langfuse trace 拼装）都固化成 checklist，**跟着走不会漏改**； - `cleanup-eval-env`：兜底清理。 - 这意味着——LIFT 不光是个框架，**还是个能让别人快速上手的产品**。

fig.14 · 总结

一张幻灯片记住

痛点
自进化常是假阳性、评测本身也不可信 SkillsBench 自生成 Skill 无效有害；安全 benchmark 排名 W=0.10
标准
每个 Suite 显式分 warmup / holdout train 进化 → test 对照
怎么打分
Judge 扮成"用户"跟 Agent 多轮对话 验收清单只在 judge 脑里，逼 agent 听反馈改
为什么是框架
脚本路线每接一个 Agent 都重抄一遍 并发、报告、judge 都得复制
核心抽象
Adapter 4 个钩子 框架不关心进化产物的形式
红利
并发 / Dashboard / Trace 关联 / Skill 接入引导，框架全兜底 新 Agent 跟着 skill 走，丝滑接入
一页带走： - 业界的痛——评测靠感觉、形式不一没法横向比； - 我们的标准——Suite 切 warmup/holdout，能测进化前后； - 工程的必然——脚本路线撑不到第二个 Agent，所以做成框架； - 关键抽象——Adapter 4 钩子，框架不关心你的进化产物长什么样； - 框架红利——并发、Dashboard、Trace 都不用接入方操心，**任何 Agent 都能丝滑接入**。 Q&A 时间。
