提交文件夹，文件夹内存放对应场景/任务类型的所有任务，文件夹格式如下：
<场景名称/任务类型>/
├── q1_<任务短名>/
│   ├── q1_<任务短名>.md
│   └── materials/
│       └── [Q1 专属补充材料]
├── q2_<任务短名>/
│   ├── q2_<任务短名>.md
│   └── materials/
│       └── [Q2 专属补充材料]
└── skills/ # 可选，如果有必要的skill就加进来
    

### 机器可读 Suite JSON（LIFT / `src_new` 评测）

预处理后的 `assets/benchmarks/*.json` 在标准 `Suite` 字段之外，可包含 **hold-out 配置**（由 [src_new/lift/suite/lift_suite.py](../src_new/lift/suite/lift_suite.py) 读取）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `holdout_count` | int，可选，默认 `1` | `tasks` 中**最后 N 题**为 hold-out（LIFT 终测对照） |
| `holdout_task_names` | string[]，可选 | 显式指定 hold-out 题名；若存在则**优先于** `holdout_count` |

- **warmup**：非 hold-out 题目，用于产生产物（默认前导题 + evolve）。
- **hold-out**：每题在 report 中各一条 `TaskRun`（`baseline` / `evolved`）。

官方评测入口：[src_new/lift/README.md](../src_new/lift/README.md)（`python -m src_new.cli.lift_main --runtime openclaw`）；legacy 仍为根目录 `openclaw_main.py --mode exam`。

任务为md文档，md文档内容格式参考任务示例，但是需要按照任务分开。以下是一个任务.md的示例：
```
### query

[任务 query。必须用自然语言说明：需要使用工作区 materials 文件夹中的哪些材料；最终产物保存到工作区 result/result_q{n} 文件夹。query 应精简，后期任务可口语化/模糊化，但不能缺失独立执行所需的关键信息。]

### 要求

1. [内容要求：输出格式、字段、组织方式、业务规则、私人定制化偏好等，必须覆盖完成任务所需的全部需求]
2. [内容要求或业务约束：核心规则校验、异常处理、取舍逻辑等]
3. [轨迹相关需求：如需进行数据解析、信息检索、可视化设计、内容生成等操作及目的]
...

### 轨迹要求

1. [从“要求”中提取出的轨迹类需求：操作类型，具体操作描述，操作目的说明]
2. [允许补充“要求”中未显式提到但完成任务必需的轨迹要求，但不得与“要求”矛盾]
...
```

任务相关要求
1. 难度设置
在每一类任务中，任务的难度最好有渐进关系，并且每一类任务最后最好有一个最终测试任务。最终测试任务需要难度较高或综合性较强可以组合之前任务所需的能力或者工作流来构造这样的任务，这是参考例子任务示例
对于构造难度渐进关系，可以尝试以下方式:
  - 扩展要求：如对同类任务，让场景更加丰富，从而扩展新的要求
  - 更改任务描述：对于类似的任务，让任务描述更精简，同时保持要求不变
  - 组合能力(适合构造最终测试任务)：对于同类任务，构造一个场景，它同时需要多个场景下的要求(比如任务示例中的Q5就是组合了日常场景(claw风评调研)和学术场景(评测方案调研))
如果发现构建起来很难，就尽量扩展场景以及对应的要求就好
2. 要求设置
  - 要求：对产物内容、格式等提出要求。如内容必须包含XXX，格式为XXX
  - 轨迹要求：对完成任务所需要的步骤提出要求。如限制搜索信息源，限制工具/skill使用(在有多个功能相似时，要求只能从中选特定的几个)，完成任务方法/编程语言限制
  在填写任务时，要求中填写内容+轨迹要求，轨迹要求是只能来自于要求中的，只不过表述上更加偏向执行过程的规范和约束，如果发现要求中的部分条目就是轨迹要求，可以直接复制到轨迹要求中，在评测时内容要求和轨迹要求是分开的，所以不能因为在要求中写了就不在轨迹要求中写。
  
最终测试的核心目的是测试进化能力是否有效，是否能泛化(在query包含历史query相关的场景下能否灵活运用好此前的要求提示)。因此，他需要有部分要求是和此前的任务要求重复的，大概50%左右，更多一点也行。

构建方法参考
1. 先从找一个任务开始，思考如果需要Agent完美的交付你脑中所想的结果，你需要怎么写query来提供足够的信息。然后逐步剔除这些信息，放到这个任务的要求中。zclawbench里面就有一些query内容比较丰富的，可以选择他们来作为第一个任务和要求的构建。
2. 任务可以参考以下构建原则：
  - 任务可以有难度变动，并且逐步变难，可选的方法有
    1. 增加任务本身的复杂度，比如从简单的信息检索收集变为信息理解并给出结论，
    2. 增加任务背景的难度，比如网络帖子的解读升级到论文的理解；又或者是增加完成任务所需的工作量，比如在任务中给出多个信息源和需要检索的目标；还可以是对之前任务涉及到的目标的组合，比如前面有搜索网络信息和论文知识的，现在就可以构造一个任务同时需要获取这两类信息，并且整合在一起。
    3. 让任务本身变模糊，可以使用日常对话风格，在任务内容中尽量少给要求和提示指引
    4. 组合多类能力、多类工作流到一个任务中
  - 最后一个任务，即最终测试，难度提升稍大一点，此前的任务应更注重任务类型覆盖的广度。
3. 要求，可以参考以下构建原则：
  - 要求仅限于提供原则/规则/建议信息
  - 同类任务中，要求可以根据任务的情况进行增减，只是不要有冲突
  - 同类任务中，要求可以针对进一步的细分场景做变动，比如信息搜集任务中舆论分析和学术调研都可以给出检索源限制，但是限制的源不同
  - 出于测试进化和学习能力的需要，可以考虑给出一些高度私人定制化的要求，来增加要求的数量，但是定制化内容不是针对单点问题的，而是能针对一类问题的私有要求。
