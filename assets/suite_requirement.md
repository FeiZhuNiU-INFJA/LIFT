# 评测数据集结构介绍及构造要求

## 介绍

[构造初衷以及为何如此设计](../docs/benchmark-intro.md)

本项目中，评测数据集分为三层结构。即**总数据集——场景数据集——训练和测试任务**

### 单个场景下的数据集格式
```text
<场景名称/任务类型>/
├── train/                    # warmup 题（产物进化）
│   ├── q1_<任务短名>/
│   │   ├── q1_<任务短名>.md
│   │   └── q1_materials/     # 每一题所需的支撑材料
│   └── q2_<任务短名>/
│       └── ...
├── test/                     # final / holdout 题（LIFT 终测对照）
│   ├── q5_<任务短名>/
│   │   └── ...
│   └── q6_<任务短名>/
│       └── ...
└── skills/                   # 可选，场景级 skill
```
数据集以**文件夹+md任务文档**的人类易读方式存储。对于这种场景级的评测集，项目中称之为`Suite`，其中的具体任务称之为`Task`
所有的单场景数据集文件夹放到同一文件夹下，他们的父文件夹即可视作一个**总数据集**。

### 机器可读 Suite JSON（LIFT / `src` 评测）

preprocess 生成的 `assets/benchmarks/*.json`（不纳入 git）使用 [src/models.py](../src/models.py) 中 ``Suite`` 结构：

| 字段 | 类型 | 说明 |
|------|------|------|
| `warmup_tasks` | `SuiteTask[]` | 对应场景下 ``train/`` 下题目，用于 warmup + evolve |
| `holdout_tasks` | `SuiteTask[]` | 对应场景下 ``test/`` 下题目，用于 holdout baseline/evolved 对照 |

- 每个 **final** 题在 report 中各一条 `TaskRun`（`baseline` / `evolved`）。

官方评测入口：[src/lift/README.md](../src/lift/README.md)（`python -m src.cli.lift_main -r openclaw`）；legacy 见 [legacy/README.md](../legacy/README.md)。

### 任务.md 示例

任务为md文档，md文档内容格式参考任务示例，但是需要按照任务分开。以下是一个任务.md的示例：
```
### query

[任务 query。必须用自然语言说明：需要使用工作区 q{n}_materials 文件夹中的哪些材料；最终产物保存到工作区 result/result_q{n} 文件夹。query 可以较为简单，语言表达尽量日常化和口语化，但是在query中出现的需求不应该拆分为多个要求，在后续的要求以及轨迹要求栏目中填写，如果必须填写，那么请合并为一个大要求填入。]

### 要求

1. [内容要求：输出格式、字段、组织方式、业务规则、私人定制化偏好等，必须覆盖完成任务所需的全部需求]
2. [内容要求或业务约束：核心规则校验、异常处理、取舍逻辑等]
3. [轨迹相关需求：如需进行数据解析、信息检索、可视化设计、内容生成等操作及目的]
...

### 轨迹要求

1. [从“要求”中提取出的轨迹类需求：操作类型，具体操作描述，操作目的说明]
2. [允许补充“要求”中未显式提到但完成任务必需的轨迹要求，但不得与“要求”矛盾]
...
```

其分为query、要求与轨迹要求三部分，各自的目的如下：
1. query：目的是模拟用户与Agent的自然交互，query中可以不包含非常充足的信息以模拟用户下达指令时并没有想好具体要求的情况
2. 要求：目的是模拟用户接收到了Agent的生成结果，根据生成结果的不足，补充自己想到的要求，以此纠正Agent的行为
3. 轨迹要求：目的是为了检查Agent用于达到任务query的目标以及后续补充的要求所采用的方案的质量，主要是工具调用的有效性以及高效性，顺便检查一下Agent的产物是否存在幻觉因素(如本应网络查询信息得到结果时选择直接生成回复)

### 评测执行流程

1. 将query发送给Agent
2. 得到Agent执行结果，通过LLM judge判定要求是否全部通过，没通过就给出要求清单中没完成的前两个要求作为提示，让Agent继续完成任务以达到要求，模拟人与Agent的交互
3. 循环步骤2直到LLM judge通过，或者达到最大尝试次数

### 训练集(Warmup Task)与测试集(Holdout Task)

在本评测数据集中，训练集的含义与普通的数据集一致，不再赘述。对于测试集则有特殊要求：
1. 测试集query所对应的任务类型需要与场景一致
2. 测试集的要求需要有**75%左右的与训练集中一致**，剩余**25%左右是训练集要求中的变体，或者是与训练集要求中矛盾的**，用于检查进化后是否过拟合与训练集中的要求，也可以是新增的要求，但是效果不如使用变体或者矛盾的方案。

#### 数据集划分

本评测默认示例使用4训练集任务+2测试集任务

#### 什么样的要求叫做与训练集中要求一致

1. 直接复制训练集中的要求
2. 要求所需操作不变/内容输出结果不变，仅表述变化或要求的背景切换

#### 什么样的要求是训练集中要求的变体/矛盾？

直接看例子：
```text
训练集要求：
...
X. 旅游规划时多去逛点人文古迹什么的
...

测试集要求：
...
X. 规划旅游路线时多加入一点自然景观优美的景点 -> 变体
...
Y. 旅游路线中不要出现人文古迹景点的参观，我不喜欢 -> 矛盾

```


## 任务构造准则与建议

### 构造准则

#### 要求与轨迹要求的设置

- 要求
  - 对产物内容、格式等提出要求。如内容必须包含XXX，格式为XXX。
  - **要求必须要可验证**，如果要求不明确，验收标准很多样的话可能会影响评测结果。
  - 要求必须处于**同一层级**，不要出现要求的子要求。
  - 要求的条目数量**至少12条以上**
- 轨迹要求
  - 对完成任务所需要的步骤提出要求，相当于对要求的完成过程进行检查。如限制搜索信息源，限制工具/skill使用(在有多个功能相似时，要求只能从中选特定的几个)，完成任务方法/编程语言限制
  
注意，要求的设计对进化能力的评测效果影响很大。一些局限性非常强的，只能适用于当前query的要求**不允许在测试集中出现**，如果任务需要补充这些信息，那就在query里面明确给出，若内容过多，也可以放到任务的materials中作为支撑材料，然后在query中引用。但是他们**可以在训练集中少量出现**，相当于对话中的一些不可泛化的噪声。

在构造任务时，要求中填写内容+轨迹要求，**轨迹要求是只能来自于要求中的**，只不过表述上更加偏向执行过程的规范和约束，如果发现要求中的部分条目也完全符合轨迹要求的标准，那么可以直接复制到轨迹要求中，当前的评测中，内容要求和轨迹要求是分开的评测的，所以不能因为在要求中写了就不在轨迹要求中写。

### 构造建议

在构造数据集的一开始，先从训练集的构造开始，再基于训练集构造测试集。以下是一个从零开始的构造思路，可供借鉴。

#### 训练集构造

1. 先从找一个任务开始，思考如果需要Agent完美的交付你脑中所想的结果，你需要怎么写query来提供足够的信息。
2. 逐步剔除除了最终交付文件以外的补充信息，放到这个任务的要求中。对于训练集来说，可以放一些针对于当前任务的补充信息作为要求，但是这些极度聚焦于当前任务的，不可泛化的要求不建议占比超过50%，不然测试集的要求构造可能无法完成

#### 难度波动

在每个场景中，**任务间**的难度最好存在波动，不过对于**训练集和测试集内**的任务不需要难度递进，即不需要q1的难度一定大于q2，但是q2和q1的难度最好不一样。

对于构造难度渐进关系，可以尝试以下方式:
  - 扩展要求(增加任务本身难度)：如对同类任务，增加问题深度、让场景更加丰富或组合多个场景，从而扩展新的要求
  - 更改任务描述(增加任务背景难度)：对于类似的任务，让任务描述更精简，同时保持要求不变少
  - 组合能力(**对于测试集的构造，必须组合训练集中的能力/要求，但场景可以不同**)：对于同类任务，构造一个场景，它同时需要多个场景下的能力/要求

#### 测试集构造

在完成了训练集数据构造后，基于他们构造测试集。由于测试集需要75%左右的要求与训练集中的要求一致，同时25%左右的要求是训练集中出现过的要求的变体或者矛盾的要求。建议先审查训练集中那些对于解决问题有指导意义的，可泛化的要求，然后基于他们尝试找到一个当前场景下的能包括这些要求的任务。然后再对这个任务进行细微的改造，让它的要求会和训练集中的任务产生不一致，从而构造剩下25%左右的要求变体或矛盾要求。如果发现难以构造，也可以选择让要求100%来自的训练集要求。或者创造25%的适用于当前任务的新要求。
